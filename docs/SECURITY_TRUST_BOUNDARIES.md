# Security Trust Boundaries

This document defines the trust boundaries for the Gate Monitoring System, identifying what is trusted, what is untrusted, and what becomes trusted only after server-side validation.

## UNTRUSTED

### Client/Browser
- **Frontend state**: All React/Next.js frontend state
- **localStorage**: All data stored in browser localStorage
- **sessionStorage**: All data stored in browser sessionStorage
- **Frontend UI controls**: Buttons, disabled states, hidden elements
- **Client-side validation**: All frontend validation logic
- **Client-generated timestamps**: Any timestamps generated by the client
- **Client-generated location data**: GPS coordinates, device location
- **Client-generated device metadata**: User agent, device information
- **Client-side role/permission checks**: Any role or permission validation done only in the frontend

### Request Data
- **Request body**: All data sent in request bodies
- **Query parameters**: All URL query parameters
- **URL parameters**: All URL path parameters (e.g., `/students/[roll]`)
- **Headers**: All HTTP headers except those set by trusted server middleware
- **QR payloads**: All data read from QR codes
- **Form data**: All form submissions
- **File uploads**: All uploaded files
- **API parameters**: All parameters sent to API endpoints

### Specific Untrusted Fields
- `request.body.operatorId`
- `request.body.userId`
- `request.body.studentId`
- `request.body.gateId`
- `request.body.role`
- `request.body.permissions`
- `request.body.timestamp`
- `request.body.direction`
- `request.body.reason`
- `request.query.roll`
- `request.params.roll`
- `request.body.pin`
- `request.body.password`

## TRUSTED ONLY AFTER SERVER VALIDATION

### Authenticated Identity
- **User ID**: Only after successful JWT verification and account status validation
- **User role**: Only after validation against current database state
- **Account status**: Only after validation against current database state (active, suspended, disabled)
- **Session validity**: Only after session validation and account status check
- **Permissions**: Only after role-based permission validation

### Resource Access
- **Student access**: Only after verifying ownership/authorization (e.g., parent-child relationship)
- **Gate access**: Only after verifying operator is authorized for specific gate
- **History access**: Only after verifying user has permission to view specific student history
- **Pass access**: Only after verifying user is authorized to view/modify specific gate pass

### Operational Data
- **Operator identity**: Only derived from authenticated session, never from request body
- **Gate context**: Only derived from authenticated session or validated gate assignment
- **Scan direction**: Only after validation of allowed values
- **Exit reason**: Only after validation of allowed values
- **Timestamps**: Only server-generated timestamps for authoritative records
- **Correction requests**: Only after validation of authorization and business rules

## HIGHLY PRIVILEGED

### System Operations
- **Service-role credentials**: Supabase service role key for privileged operations
- **System-admin operations**: Operations that modify system configuration
- **Role management**: Operations that change user roles
- **Account suspension/disabling**: Operations that change account status
- **Audit log operations**: Operations that read audit logs
- **Bulk data operations**: Student record imports, mass updates
- **Credential reset**: Operations that reset user credentials
- **Database migrations**: Schema changes and data migrations

### Security Operations
- **JWT secret**: Used for token signing and verification
- **Supabase admin key**: Used for service-level operations
- **Environment variables**: All sensitive configuration
- **Password/PIN hashing**: Cryptographic operations for credential storage
- **Session management**: Session creation, validation, and invalidation

## TRUST FLOW

### Authentication Flow
```
Untrusted Request → JWT Verification → Authenticated Identity → Account Status Validation → Authorized Session
```

### Authorization Flow
```
Authorized Session → Role Validation → Permission Check → Resource Authorization → Operation Execution
```

### Gate Scan Flow
```
Untrusted Request (roll, direction, reason) → Authentication → Operator Validation → Gate Authorization → Student Validation → Business Rule Validation → Record Creation
```

### Student Data Access Flow
```
Untrusted Request (roll) → Authentication → Role Validation → Student Authorization → Field-Level Filtering → Data Return
```

## SECURITY PRINCIPLES

1. **Never trust client-supplied IDs**: All identifiers (userId, studentId, gateId, operatorId) must be validated against authenticated session and authorization rules

2. **Server-side authorization**: All authorization decisions must be made server-side based on validated session data

3. **Data minimization**: Only return the minimum necessary data for each operation based on user role

4. **Immutable audit**: All security-relevant operations must be recorded in immutable audit logs

5. **Fail securely**: Any validation failure should result in access denial

6. **Defense in depth**: Multiple layers of validation (authentication, authorization, business rules)

7. **Zero trust**: Every request is treated as potentially malicious until proven otherwise
