# PR-05 (Escalation + SLA) + PR-06 (Decision Engine) + PR-07 (Delegation Engine)

> One migration (they are one institutional loop: case → policy/authority
> → escalation when refused → decision → delegation that produced it →
> audit). The principal is a policy/authority node, not a page.

## PR-05 · Escalation + SLA Engine

**Goal:** teach the system *when* something should move upward. Escalation
is generated by policy, not by frontend code.

**Changes:**
- `escalations` — the durable escalation record. Carries an explicit
  reason (PR-01 `EscalationReason`), severity, source, target role +
  context, the authority_ids considered, a deadline, structured evidence,
  and a recommended action. The principal sees **why**, not just
  "new request".
- `sla_instances` — the clock a case runs on. `breachSla()` flips a
  running instance to `BREACHED` and generates the `SLA_BREACH`
  escalation. Called by the worker/cron sweeper, never by UI code.
- `escalate(input)` — the policy entry point. Called by the authority
  engine on refusal, by the SLA sweeper on breach, by a risk jump, or
  manually. Appends the escalation to the case's event stream (PR-02)
  and writes the audit event.

**Exit condition (met):** "Escalation is generated by policy, not by
frontend code." An authority refusal generates an `AUTHORITY_INSUFFICIENT`
escalation (proven by the DB test: a 15-day hostel_manager request is
refused → escalation row exists, the case stays put, no decision).

## PR-06 · Decision Engine

**Goal:** a consequential action produces a durable Decision record —
never just `PATCH /ticket status = approved`.

**Changes:**
- `decisions` — the durable record: `decision_no` (DEC-YYYY-NNNN),
  case_id, operation (PR-01 StandardOperation), actor + role +
  role_context, authority_source (role / delegation / emergency_override),
  the exact `authority_ids` that allowed it, `delegation_id` when
  satisfied via a grant, reason, evidence, the impact preview, and the
  previous/resulting state.
- `decision_signatures` — the credential that signed a decision
  (an audit event id, a document-signature id, or a JWT). The signature
  is the proof, not the assertion.
- `recordDecision(input)` — mints the decision, moves the case
  lifecycle (approve → resolve, reject → cancel, via PR-02), appends
  the decision to the case's event stream, and writes the audit event.
- `decideAndTransition(caseId, action, actor, definition, bounds, reason, impact)`
  — the one entry point a migrated domain calls: authority check →
  (refused? escalate, don't move) → workflow transition → durable
  decision. This is the institutional loop.

**Exit condition (met):** "A consequential action produces a durable
Decision record." Proven by the DB test: an approved 15-day gate_pass
produces a `DEC-YYYY-NNNN` row that pins actor + role_context
(`chief_warden`) + authority_source (`role`) + the exact authority rule,
and is queryable from the ledger (not just in memory).

## PR-07 · Delegation Engine

**Goal:** Principal → VP/HOD/etc. authority delegation as a *bounded
authority grant*, not a role switch.

**Changes:** none to the schema — the bounded grant already lives in
`delegations` (entity_foundation), and the matching already runs in
PR-04's delegation-aware `authorize()`. PR-07 is the *engine*: a
delegatee with an active, unrevoked, in-window delegation **can** act as
the delegated role within the scope window; nothing is permanent.

**Exit condition (met):** "The authority engine automatically recognizes
active delegation." Proven by the DB test: a vice_principal with a live
delegation to act as `principal` on `gate_pass` approvals is satisfied
*via the grant* (the VP's direct role has no such policy), and the
resulting decision is marked `authority_source = 'delegation'` + the
grant id.

## Shared manifest

**Depends on:** PR-02 (case), PR-03 (workflow), PR-04 (authority).

**Migration required:** `20270130000003_institutional_decisions.sql`
(+ `.down.sql`). Four new tables (`escalations`, `sla_instances`,
`decisions`, `decision_signatures`). `escalations.case_id` +
`decisions.case_id` → `cases.id` (PR-02). `decisions.authority_ids`
jsonb cites `authority_policies.id` (PR-04). No RLS on the universal
tables in this PR (admin manages, gate_app writes decisions/escalations,
everyone reads).

**API changes:** the decision surface is the engine
(`recordDecision` / `decideAndTransition`). The HTTP routes
(`/api/decisions`, `/api/decisions/:id/execute`, `/api/escalations`,
`/api/escalations/:id/resolve`) land with PR-12 (Principal Command
Center), which is the natural consumer. PR-06's exit condition is the
durable record, not the UI.

**Security impact:** every consequential action now produces a decision
that pins the authority source + the exact policy + the delegation grant
(when applicable). This is the substrate PR-11 (audit hardening) and
PR-14 (SoD + security) build on: "Can an expired delegation still
work?" / "Can a delegated authority exceed its scope?" are now
answerable from the decision ledger, not from a diff of a PATCH.

**Tests:** `tests/unit/institutional-decisions.test.ts` (3 DB-backed
assertions: the refusal → escalation path, the approve → durable-decision
path, and the delegation-satisfied decision). Migration replayed clean
on a scratch `supabase/postgres:17` container.

**Rollback:** `.down.sql` drops the four tables; delete the engine file.
No domain data is affected.
