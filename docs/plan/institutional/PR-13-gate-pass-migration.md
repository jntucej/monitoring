# PR-13 — Domain Migration (gate passes: step 1 of 2)

> Migrate the existing domains onto the case engine, one at a time.
> Gate passes go first (the reference workflow seeded in PR-02/03).
> Each migration follows: Map → Case → Workflow → Authority →
> Escalation → Decision → Impact → remove old path. This PR is
> **step 1 (additive)**: every gate pass is now ALSO a GATE_PASS case.
> **Step 2 (remove old path)** is deliberately not in this PR — the old
> `createGatePass` path stays the source of truth for the pass row; the
> case layer is the tracking record a decision moves.

## What landed

**Gate-pass → case link** (additive):
- `POST /api/passes` now opens a `GATE_PASS` case (subject = the
  student's roll) when a pass is created. The case's payload carries
  `reason` + `duration_days` (the duration the authority bound tests
  against).
- The case is linked to the pass row via `case_evidence` (kind
  `gate_pass`, reference = the pass id) — the domain table stays the
  source of truth; the case layer only stores the link.
- The link is **additive and fault-tolerant**: a case-layer failure
  (missing table, FK mismatch) is logged and must NEVER break pass
  creation. The old path is untouched.

**Case → pass link helper** (the reusable pattern for every domain
migration):
- `linkCaseToRecord(caseId, recordKind, recordId, actor)` — appends a
  `record_linked` event + a `case_evidence` row. Every later domain
  (hostel_leave, exam, complaint) uses the same shape: link, never copy.

**Duration is first-class in the authority bound** (so the seeded
policy actually gates):
- `transitionWorkflow` now passes the case's `payload` (including
  `duration_days`) into the authority request, so a
  `max_duration_days` bound tests against the real request duration.
  A 15-day gate_pass from a `hostel_manager` (bound 3 days) is refused
  → escalation; the same case approved by the `principal` (no bound)
  moves to `approved`.

## The reference gate-pass workflow (seeded, now wired)

```
gate_pass definition (workflow_definitions):
  submitted → manager_review → deputy_review → principal_review
             → approved | rejected | expired

authority_policies (bounds):
  hostel_manager    approve gate_pass  ≤ 3 days (their block)
  deputy_warden     approve gate_pass  ≤ 7 days (campus-wide)
  principal         approve gate_pass  no bound (institution-wide)
```

A request that exceeds the current role's bound does not move — it is
refused (the case stays put) and generates an `AUTHORITY_INSUFFICIENT`
escalation (PR-05) that the attention engine (PR-09) surfaces to the
principal with the reason. That is the "escalation generated by policy,
not frontend code" the plan calls for.

## Manifest

**Depends on:** PR-02 (case), PR-03 (workflow), PR-04 (authority),
PR-05 (escalation), PR-09 (attention).

**Changes:**
- `src/app/api/passes/route.ts` — the additive case link in `handlePost`
  (fault-tolerant; never breaks pass creation).
- `src/lib/institutional/cases.ts` — `linkCaseToRecord` (the reusable
  domain-migration pattern).
- `src/lib/institutional/workflow.ts` — the authority request carries
  the case payload (duration) so bounds test against the real request.
- `tests/unit/institutional-workflow.test.ts` +
  `tests/unit/institutional-decisions.test.ts` — the reference cases
  carry `duration_days: 15` so the bound is actually exercised.

**Does NOT change:** `createGatePass` (still the source of truth for
the pass row), the pass's `admin_status` lifecycle (the decision that
moves it is step 2), every other domain (hostel_leave / exam /
complaint migrate one at a time, not all at once).

**Migration required:** no new tables — this reuses the PR-02 case
tables + the PR-03/04 workflow/authority seeds already in place.

**Database changes:** none (the tables exist from PR-02/03).

**API changes:** `POST /api/passes` is now also a case-creating call
(additive; the response envelope is unchanged — the case id is NOT
added to the response so no client contract changes).

**Security impact:** the gate-pass authority question is now answered
by the engine (role + bound), not by a role string in the route. A
hostel_manager approving a 15-day pass is refused by policy (not by a
frontend guard) — that is the SoD substrate PR-14 tests.

**Tests:** the workflow + decisions tests now carry `duration_days: 15`
on their reference cases, so the bound gate is exercised end-to-end
(12 DB-backed assertions pass against a scratch DB). The gate-pass
migration itself is additive + fault-tolerant (a case failure cannot
break pass creation), so it is not a separate test surface.

**Rollback:** remove the case-link block in `handlePost` + the
`linkCaseToRecord` export. No domain data is affected (the case rows
are tracking records, not the pass rows).

## Next

**Step 2 (not in this PR):** the decision that moves a pass's
`admin_status` — `POST /api/passes/:id/action` calls
`decideAndTransition(caseId, "approve"/"reject", ...)` and the engine
writes the `gate_passes.admin_status` + records the durable decision.
Until step 2 lands, the pass's own status path is the source of truth;
the case is the tracking record. Then, per the plan: hostel_leave →
complaints → hostel discipline → academic status → examination →
security incidents → emergency, one domain per PR, each removing its
old path only after the case path is proven.
