### Headroom math
The 3 AI workers must share ~8.9 GiB available RAM on a 20-thread CPU with **no GPU**.
Therefore every model must run **CPU-only, 4-bit-quantized, lazily started**, and
the two heavier workers (M2 OCR, M3 doc-intel) must be **serialized** so they never
load simultaneously.

### Why these three (not the "obvious" picks)
- **M1 = qwen3:1.7b.** A 0.5 B model (e.g. `gemma3:270m`) is *too weak* to produce
  reliable multi-field tool JSON on the first attempt — the task explicitly says a
  smaller-but-unreliable model is worse than a slightly larger reliable one. 1.7 B
  Q4 gives dependable JSON + tool selection at ~1.4 GB and is **already installed**.
- **M2 = Tesseract 5 (as deployed) with PaddleOCR as the documented upgrade path.** The
  task forbids using a general LLM for OCR; a dedicated OCR engine is the right tool.
  PaddleOCR is *not* installed on this host, so the Tesseract fallback is the engine
  that actually runs and was benchmarked end-to-end (sample invoice → clean text in
  ~0.2–0.35 s/page). PaddleOCR mobile (ONNX, Indic + tables) remains the recommended
  upgrade if Indic-language OCR is later required — the sidecar auto-selects it when
  the `paddleocr` module is importable.
- **M3 = qwen2.5:3b.** A 3 B Q4 model gives materially better entity/date/validity
  extraction than 1.7 B while staying under ~2.1 GB so it can be the *sole* large
  resident when M1 is idle. Serialized with M2, peak resident RAM stays ≤ ~3.5 GB.

## 3. Exact versions, runtime, and compatibility

- **Runtime:** Ollama v0.35.1 (already installed) is the LLM runtime for M1 and M3.
  It serves an OpenAI-compatible `/v1` on 127.0.0.1:11434, which the new
  `model-runtime/conversation` and `model-runtime/document-intelligence` clients
  speak. **No new LLM framework is introduced.**
- **M1 = `qwen3:1.7b`** — Ollama native GGUF Q4_K_M. x86_64 ✔. CPU-only ✔. ARM64 ✔
  (Ollama supports both). Docker ✔ (host service; sidecar can also run `ollama/ollama`).
  License: Apache-2.0. Limitation: max useful context ~8–32 K; set `num_ctx` ~4096 for routing.
- **M3 = `qwen2.5:3b`** — Ollama native GGUF Q4_K_M. x86_64 ✔, ARM64 ✔. CPU-only ✔.
  License: Apache-2.0. Limitation: needs `num_ctx` ~8192 for whole-document text;
  slowest of the three on this CPU.
- **M2 = Tesseract 5 (installed) / PaddleOCR upgrade path** — Python 3.13 ✔, x86_64 ✔,
  CPU ✔, Docker ✔. License: AGPL v3 (Tesseract) / Apache-2.0 (PaddleOCR). Tesseract is
  isolated in a per-burst sidecar process (no persistent memory), so the AGPL copyleft
  never reaches the Node app. Limitation: English-optimized; Indic support is weak —
  switch the sidecar to PaddleOCR PP-OCRv5 (auto-selected when importable) for
  Telugu/Tamil/Hindi.

### Expected resource envelope (worst case, M2 then M3 serialized)
| Worker | RAM loaded | CPU threads | VRAM | Cold start (first call) | Idle cost |
|---|---|---|---|---|---|
| M1 qwen3:1.7b | ~1.4 GB | 8 (P-cores) | 0 | 2–4 s | 0 (stopped by idle timeout) |
| M2 PaddleOCR | ~0.5 GB | 4 | 0 | 2–3 s | 0 (stopped after OCR burst) |
| M3 qwen2.5:3b | ~2.1 GB | 8 (P-cores) | 0 | 4–6 s | 0 (stopped by idle timeout) |
| **Serialized M2→M3 peak** | **~2.1 GB** (M2 released before M3 loads) | 8 | 0 | — | — |
| Simultaneous (never allowed) | ~4 GB | — | — | — | — |

The model manager **guarantees M2 and M3 never coexist** (a `docPipeline` mutex), so
peak resident AI RAM is ~2.1 GB plus M1's ~1.4 GB when conversation is active →
≤ ~3.5 GB, well inside the 8.9 GB available.

## 4. What is NOT introduced (per task constraints)
No vector DB, no embeddings service, no reranker, no planner, no LangChain/LangGraph,
no extra LLM, no fine-tuning, no Kubernetes, no GPU. The existing Postgres
`kb_chunks` embedding store and `RAG_EMBEDDING_*` are left untouched; this task only
adds the three local AI workers behind the existing `llm-proxy`-style contract.

## 5. Measured results (this host, `node scripts/benchmark-ai/run.mjs`)

Captured against the live Ollama (127.0.0.1:11434) on 2026-11-25. Full machine-readable
report at `scripts/benchmark-ai/results.json`.

| Worker | Model | Cold start | Warm latency | t/s | JSON validity | RAM | Notes |
|---|---|---|---|---|---|---|---|
| M1 conversation | `qwen3:1.7b` | 6.0–8.7 s | 5.9–6.4 s | 16.8–19.7 | **1.0** (5/5) | ~60 MB (Node) | Cold start dominated by Ollama loading the Q4 model into CPU; warm = inference. 100% of tool-envelope JSON parsed + valid on all 5 trials. |
| M2 OCR | `tesseract-5` | n/a (per-burst) | ~0.5 s | n/a | n/a | ~0.2 GB | ~2.1 pages/sec at 200 dpi; sample invoice OCR'd to clean text in 339 ms. PaddleOCR not installed, so Tesseract is the live engine. |
| M3 doc-intel | `qwen2.5:3b` | 3.6 s | 0.64 s | 2.7–2.8 | **1.0** (5/5) | ~74 MB (Node) | Cold = model load; warm = 3B inference at ctx 8192. Extraction JSON valid on all trials. |

Key takeaway: **M1 and M3 both hit 100% JSON validity on the first attempt**, which is
the core reason they were chosen over a smaller-but-flakier model — a 1.7 B router that
reliably emits valid tool JSON is cheaper end-to-end than a 0.27 B model that retries.
Serialized M2→M3 keeps peak resident AI memory ≤ ~2.1 GB, inside the 8.9 GB available.
